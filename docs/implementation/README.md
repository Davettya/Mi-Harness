# 实现指导入口

本目录将 [系统设计 1.0](../通用Agent-Harness系统设计文档.md) 转化为 **13 份按职责分工的实现规范**。适用形态为本地服务 + Web；技术路线沿用既有设计。本次只整理和细化实施方式，没有创建应用代码、安装依赖或执行系统验收。

## 1. 阅读与使用方法

开始开发先读 [01 公共契约](01-contracts.md)，再读所负责的模块及其前置依赖；按本页里程碑安排实施，验收统一到 [13](13-verification.md)。编号用于引用与定位，不代表必须依次串行开发。

原总体设计与 `research/` 保留为决策背景和证据快照，停止作为另一份同步更新的实现规范。开发细节以本目录各主题的唯一所有者为准；修改时同步维护契约调用者，不复制一份规则到其他文档。

所有拟议目录、接口、配置和测试用例均是待实现内容。涉及上游 SDK 的具体 API，开发时先按依赖锁文件验证；不把原调研日期的结论当成未来版本保证。

## 5. 一条最小纵向实现路径

依次打通“认证进入工作台 → 创建工作区/会话 → 提交输入持久入队 → worker 运行 → 模型请求读取工具 → Gateway 执行并存结果 → 最终回复结算 → SSE 与断线重连”。先使用确定性假模型和无副作用工具，再加入真实模型、文件写入、审批、Skills 与 MCP。

纵向路径只规定集成顺序；HTTP 形状查 10，运行状态查 06，权限判断查 12，工具账本查 07。不能为原型额外写一条绕过这些接口的“快捷执行通路”。

## 7. 文档维护与交付规则

每篇文档的“交付物”对应一个可提交工作包。新增功能先确定所有者，再补唯一接口与测试；其他文档只链接该定义。允许为解释调用关系提及其他模块，但不重复其状态表、schema、算法与验收步骤。

合并前检查链接、共享字段名、P0/P1 标记与测试编号。实现落地后将证据记录在 `docs/compatibility/` 和 `evals/results/`，不能把规范中的“应当”改写成没有证据的“已支持”。
